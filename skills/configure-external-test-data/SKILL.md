# Configure External Test Data with VUnit

1. **Use external processing when useful.** VUnit supports generating simulation inputs and checking outputs using Python or external programs. Consider this approach when reference models, algorithms, or data processing are easier to implement outside HDL. Keep verification inside the testbench when that is simpler.


2. **Use VUnit's pre- and post-simulation callbacks.** Configure `pre_config` to prepare data before simulation and `post_check` to evaluate results afterward. Use `set_pre_config` and `set_post_check` for existing configurations, or pass callbacks to `add_config` when creating named configurations.

   - `pre_config` runs before simulation and must return `True` for simulation to proceed.
   - `post_check` runs only after a passing simulation and must return `True` for the test to pass.
   - Returning `False` from either callback causes the test to fail.

   A test may use `pre_config`, `post_check`, or both, depending on its needs. Do not introduce a callback when it serves no purpose.

3. **Use the appropriate data directories.** VUnit provides paths for accessing generated data and existing project files.

   - **`output_path`:** A directory unique to each test execution. Use it for data generated by `pre_config` and outputs produced during simulation. This supports parallel execution without file conflicts.
   - **`tb_path`:** The directory containing the testbench source. Use it as a starting point for locating existing project data files whose locations are known in advance.

   Both paths are available to HDL testbenches through automatically populated generics or parameters, or through functions using `runner_cfg`.

   For example, in VHDL:

   ```vhdl
   -- File generated by pre_config
   constant generated_file : string :=
     output_path(runner_cfg) & "/input.txt";

   -- Existing project data file
   constant project_file : string :=
     tb_path(runner_cfg) & "data/input.txt";
   ```

   **Avoid `simulator_output_path` for user-developed testbenches.** It identifies a shared simulator working directory, which can cause conflicts between parallel test executions. Its primary use case is supporting third-party IP that expects files in the simulator's current working directory, such as memory models loading initialization files.

4. **Implement the callbacks.** For example, a testbench that reads input values from a file, feeds them to the design, which increments them, and writes their incremented values to another file can use:

   ```python
   from pathlib import Path

   def prepare_input(output_path):
       Path(output_path, "input.txt").write_text("1\n4\n")
       return True

   def check_output(output_path):
       result_file = Path(output_path, "result.txt")
       if not result_file.exists():
           print("Missing simulation result")
           return False

       actual = result_file.read_text().splitlines()
       expected = ["2", "5"]

       if actual != expected:
           print(f"Expected {expected}, got {actual}")
           return False

       return True

   test = lib.test_bench("tb_incrementer").test("test_increment")
   test.set_pre_config(prepare_input)
   test.set_post_check(check_output)
   ```

   The callbacks are independent. For example, use only `pre_config` when the testbench performs its own checking, or only `post_check` when the simulation generates data that must be checked externally.

   The example uses plain text files for simplicity. Choose file formats and reference-model placement appropriate to the task. Provide useful diagnostics when external checking fails.

5. **Keep data generation reproducible.** A `pre_config` callback can accept VUnit's `seed` argument to generate reproducible randomized data. Use VUnit's seed management rather than implementing a separate seeding mechanism. Follow the `randomization` skill when randomized external data is needed.

   Keep related inputs, expected results, and simulation outputs associated with the same test execution.

6. **Distinguish per-test checking from post-run processing.** The `post_check` callback is specific to a test execution and is skipped if its simulation fails.

   VUnit also supports a `post_run` callback passed to `vu.main()`. It receives a `Results` object after test execution and can inspect the overall test report, including failed tests.

   Use `post_run` for run-wide processing such as aggregating results, producing additional reports, or collecting artifacts. Do not treat it as a replacement for per-test `post_check` or assume it runs after every kind of startup or compilation failure.

7. **Integrate external tools when appropriate.** Call external programs from the callbacks when the verification task requires them. Check their exit status and handle failures explicitly. Avoid unnecessary dependencies or external processing when equivalent verification can be performed more simply in VHDL or Python.

8. **Validate the workflow.** Verify that input preparation succeeds, the simulation reads the intended data, and external checking detects incorrect or missing results. Test the workflow with parallel execution where relevant, ensuring that independent test runs do not interfere with each other's files.
